# Database

PostgreSQL 16, accessed through Prisma 6. Schema: `apps/server/prisma/schema.prisma`;
migrations: `apps/server/prisma/migrations/` (applied with `prisma migrate deploy`).
This document lists every table, column, index and constraint, which data is
authoritative, how writes are grouped into transactions, and how the server recovers
after a crash.

Related documents: [ARCHITECTURE.md](ARCHITECTURE.md#7-data-model-phase-1),
[DEPLOYMENT.md](DEPLOYMENT.md) (migrations, backups),
[API.md](API.md) (which endpoint reads what).

## Data categories

| Category                  | Tables                                                              | Written                                    | Authority                                                                                  |
| ------------------------- | ------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------ |
| **Source of truth**       | `world_checkpoint`, `snapshot`, `civilization`, `simulation_config` | checkpoint / snapshot / lifecycle          | The gzip state blob is the complete world. Nothing else is needed to continue a run.       |
| **Projections** (derived) | `building`, `household`, `citizen`, `citizen_skill`                 | in the same transaction as each checkpoint | Normalised copy of the checkpoint state for indexed queries. Rebuildable from the blob.    |
| **Append-only history**   | `simulation_event`, `event_entity`, `metric_sample`                 | with the checkpoint that produced them     | The record of what happened. Never updated; rows are deleted only by a rewind or a delete. |
| **Audit** (append-only)   | `audit_log`                                                         | with each control action                   | Who did what, when. Not simulation history; survives civilization deletion.                |

The current state is **never reconstructed from events**: the log is an audit trail of
what happened, and the checkpoint blob is the state. The engine is deterministic, so
the blob plus the seed fully explain every later state.

## Tables

Conventions: all timestamps are `TIMESTAMPTZ(3)`; `civilization_id` is a UUID; entity
ids (`id` of building/household/citizen) are the engine's integer ids, unique per
civilization; foreign keys use `ON UPDATE CASCADE` and the `ON DELETE` rule listed.

## Transaction boundaries

Source: `apps/server/src/persistence/store.ts`. Every multi-row change that must stay
consistent runs in **one interactive transaction** (`maxWait` 10 s, `timeout` 120 s for
the large ones). Bulk inserts are chunked (5,000 rows per `createMany`, ≤ 30,000 bind
parameters per projection upsert statement).

| Operation                   | One transaction containing                                                                                                                                                                                                                                                                                                                                            |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Genesis** (create)        | `civilization` + `simulation_config`, genesis events and their entity refs, the tick-0 metric sample, full projection, checkpoint, audit `civilization.created`                                                                                                                                                                                                       |
| **Checkpoint**              | buffered events + refs and metric samples, changed projection rows (or a full rebuild after a failure), checkpoint upsert, `civilization.current_tick` and `status`, and the audit entry of the control action that caused it (pause, step), if any                                                                                                                   |
| **Control action**          | (when no checkpoint is needed) `civilization.status` and/or `speed` + the audit entry (`simulation.started`, `simulation.paused`, `simulation.speed_changed`). The runner changes its in-memory state only after this commit; a failed write changes nothing. Pausing always makes `PAUSED` durable                                                                   |
| **Snapshot**                | (after a checkpoint of the current tick) the snapshot row + audit `snapshot.created`                                                                                                                                                                                                                                                                                  |
| **Rewind** (restore, reset) | delete events with `seq ≥ fromSeq` (refs cascade) and samples with `tick ≥ fromTick`; insert replacement history (genesis records on reset); mark later snapshots `detached_at`; full projection rebuild; checkpoint; `current_tick`, `status = PAUSED`, `halt_reason = NULL`, `timeline + 1`; a pending, not yet recorded `simulation.halted` entry; the audit entry |
| **Halt**                    | `status = HALTED`, `halt_reason`, audit `simulation.halted` with the reason and the violations                                                                                                                                                                                                                                                                        |
| **Unloadable state**        | `status = HALTED`, `halt_reason = 'Stored state could not be loaded: <reason>. Restore a snapshot or reset.'`, audit `simulation.state_unloadable`; skipped when the civilization is already halted with that reason                                                                                                                                                  |
| **Delete**                  | audit `civilization.deleted`, then delete the civilization (everything else cascades)                                                                                                                                                                                                                                                                                 |
| **Restart recovery**        | per interrupted civilization: `status = PAUSED` + audit `simulation.paused_on_restart`                                                                                                                                                                                                                                                                                |

A restore keeps exactly the history that leads to the restored state
(`fromSeq = snapshot.next_event_seq`, `fromTick = snapshot.tick + 1`); a reset removes
all history (`fromSeq = 1`, `fromTick = 0`) and re-inserts the regenerated genesis. The
store refuses a rewind whose replacement history is inconsistent with the target
state.

Projection writes are **diffed**: the server remembers what it last wrote and upserts
only changed rows (`INSERT … ON CONFLICT … DO UPDATE`), stamping them with
`updated_tick`. That is why `updated_tick` is per row and the tick the projection as a
whole represents is `civilization.current_tick`. After a failed checkpoint the next one
rebuilds every row.

## Read consistency

- **Projection reads** (citizen and building lists and details) run in a
  `REPEATABLE READ` transaction that also reads `civilization.current_tick`. Because
  the projection and `current_tick` are written in the same checkpoint transaction,
  the returned `asOfTick` labels exactly the rows returned — never a mix of two
  checkpoints. A running simulation's projection is at most one checkpoint interval
  (`CHECKPOINT_INTERVAL_MS`, default 2 s) behind the in-memory state; a paused one is
  exact.
- **History reads** only ever see committed events and samples, i.e. history that
  belongs to a durable state.
- **Exports** (`events.ndjson`, `metrics.csv`) are streamed page by page in separate
  queries. They are cut at the durable tick and event seq observed when they start, so
  rows that later checkpoints commit while the export streams are never included.
  A rewind or a delete, however, removes or replaces rows, so each page is checked
  after it is read and before it is sent: if `civilization.timeline` changed (a restore
  or reset committed) the export fails with `CONFLICT`, and if the civilization is gone
  with `NOT_FOUND`. Because the response is already streaming, the error aborts the
  transfer (the client sees a reset connection and an incomplete chunked body). Under
  `READ COMMITTED`, any rewind that could have affected a page has committed before the
  check's snapshot, so the check sees it: an export is either one consistent timeline
  or visibly incomplete.
- **Layout and frame** come from the in-memory simulation (not the database) and are
  labelled with the in-memory tick.

## Crash and restart recovery

- **What a crash can lose**: only the ticks simulated since the last committed
  checkpoint (at most about one `CHECKPOINT_INTERVAL_MS` of simulation while running;
  nothing while paused, because pausing and stepping commit a checkpoint, or pausing a
  status-only update, before they return).
  Events and metric samples are committed only together with the state that produced
  them, so the database never holds events without their state or a state without its
  events.
- **Why that loss is harmless**: the engine is deterministic and the lost ticks are
  re-simulated identically when the civilization runs again (same events, same seq
  numbers, same metrics).
- **On startup** the server lists civilizations stored as `RUNNING` (they were
  interrupted). With `RESUME_RUNNING_ON_START=true` it loads each from its checkpoint
  and continues running (audit `simulation.resumed_on_restart`); otherwise — the
  default — it marks them `PAUSED` with an audit entry. A civilization whose stored
  state cannot be loaded is marked halted (below); one that fails to resume for another
  reason is paused.
- **A runner paused in memory but still `RUNNING` in the database** (because writing
  the pause failed) is never unloaded by idle eviction, so it cannot be reloaded as
  running; pausing again retries the write, and shutdown writes `PAUSED`.
- **On a graceful shutdown** (SIGINT/SIGTERM) the server stops accepting requests,
  closes streams and writes a final checkpoint for every loaded civilization (forced
  exit after 30 s).
- **Corrupt data**: a checkpoint or snapshot whose blob fails schema validation, hash
  verification or an invariant is refused with an error rather than used. For the
  current checkpoint (corrupt or non-gzip blob, failed verification, invariant
  violation, or a missing checkpoint row) the civilization is marked `HALTED` with
  `halt_reason` "Stored state could not be loaded: _reason_. Restore a snapshot or
  reset." and a `simulation.state_unloadable` audit entry, and requests that need the
  world return `500`. **Recovery**: `POST …/reset` (regenerates the world from the seed
  and configuration stored in `civilization` and `simulation_config`) or
  `POST …/snapshots/:snapshotId/restore` (uses a verified snapshot). Neither needs the
  corrupt checkpoint; both rewrite it and the projections in one rewind transaction.
  If no snapshot is wanted and history must be kept, take a `pg_dump` first. A
  checkpoint written by another state schema version is not corrupt: it is refused with
  `409 CONFLICT` and left untouched for a server of the matching version.
- **Halts**: an invariant violation drops the uncommitted ticks, records the halt and
  reloads the last durable checkpoint into memory, so the stored state remains the
  last good one. A halted civilization can be restored from a snapshot or reset. A
  halt not yet recorded when a rewind commits is recorded in the rewind transaction.

## Size and retention

Measured on PostgreSQL 16 with the production build of the server on 2026-10-15
(engine as of commit `88d349b`; seed `demo-1`, default configuration, 240 ticks = 10
days, one metric sample per tick). State sizes are the `size_bytes` and
`length(state)` of a snapshot taken at tick 240; the metric row size is
`avg(pg_column_size(values))`:

| Population | State JSON | Stored gzip blob | Events | Event refs | Metric samples (avg JSONB size) |
| ---------- | ---------- | ---------------- | ------ | ---------- | ------------------------------- |
| 100        | 56,767 B   | 8,247 B          | 174    | 368        | 241 (613 B)                     |
| 1,000      | 558,973 B  | 69,476 B         | 1,653  | 3,647      | 241 (613 B)                     |

Observations and consequences:

- Genesis dominates the Phase 1 event log (one `CitizenCreated` per citizen plus one
  `MoneyIssued` per adult); afterwards only weather, season and life-stage events
  occur (5 environment events in the first 240 ticks for this seed, plus 6
  `LifeStageChanged` events at 1,000 citizens). Phase 2+ will produce far more events.
- Metric samples grow linearly with simulated time: one ~613-byte JSONB row per
  sampled tick, i.e. about 14.7 kB per simulated day at `metricsInterval = 1`. Set
  `metricsInterval` higher for long runs.
- Each snapshot stores a full gzip blob (8–69 kB above); snapshots are kept until the
  civilization is deleted. The snapshot list endpoint returns at most 500.
- The checkpoint row is overwritten in place, so its size does not grow with time.
- There is no automatic retention or pruning in Phase 1. Deleting a civilization
  removes all of its data (cascade) except its audit entries.
